# قواعد و قراردادهای پروژه YUMA

## زبان و پیام‌ها

- **تمام متن‌های کاربرپسند فارسی‌اند:** رابط کاربری، پیام خطا، اعتبارسنجی، پیامک، ایمیل، لاگ‌های سطح کاربر.
- **کامنت‌ها و مستندات کد فارسی‌اند**؛ نام متغیر، تابع، فایل و کلید API انگلیسی‌اند.
- پیام‌های تکراری در منبع واحد نگه داشته می‌شوند، نه پخش‌شده در کد:
  - سرور: `apps/api/src/common/messages.fa.ts`
  - موبایل: `apps/<app>/locales/fa.json`

## نام‌گذاری

| مورد | قاعده | نمونه |
| --- | --- | --- |
| فایل کامپوننت React | PascalCase | `JalaliDatePicker.tsx` |
| فایل ماژول/سرویس | kebab-case یا camelCase طبق عرف اپ | `orders.service.ts` |
| متغیر و تابع | camelCase | `calculateBusinessDays` |
| ثابت | UPPER_SNAKE_CASE | `ORDER_STATUS_FLOW` |
| تایپ و اینترفیس | PascalCase بدون پیشوند `I` | `OrderAddress` |
| جدول و ستون دیتابیس | snake_case | `order_items`, `created_at` |
| فیلد API | camelCase | `createdAt` |

## TypeScript

- `strict` فعال است. `any` ممنوع؛ در صورت نیاز `unknown` + narrow کردن.
- برای ورودی بیرونی (API، فرم) از Zod یا `class-validator` استفاده کنید، نه cast.
- از `as` برای ساکت‌کردن خطا استفاده نکنید.
- تایپ‌های مشترک در `@yuma/types`، تایپ مخصوص اپ در خود اپ.

## معماری و مرزها

- کد مشترک بین دو اپ **باید** به `packages/*` منتقل شود؛ کپی‌کردن ممنوع.
- اپ‌ها با هم از طریق API حرف می‌زنند (نه import متقابل).
- در NestJS:
  - کنترلر: فقط HTTP و DTO و مستندسازی.
  - سرویس: منطق دامنه و قواعد کسب‌وکار.
  - ریپازیتوری/Prisma: دسترسی داده. سرویس مستقیماً `PrismaClient` را صدا نمی‌زند.
- هیچ `process.env` یا `env()` مستقیمی در منطق دامنه نباشد؛ از config استفاده کنید.
- اعتبارنامه‌های سرویس‌های بیرونی از `.env` → `config` می‌آیند، نه ثابت‌های کد.

## دامنه و داده

- **پول:** عدد صحیح به ریال در دیتابیس؛ نمایش به تومان.
- **تاریخ:** ذخیره ISO میلادی (UTC)؛ نمایش شمسی با `@yuma/persian`.
- **جهت:** RTL؛ در وب با `dir="rtl"` و در موبایل با `I18nManager`.
- **ارقام:** پیش از اعتبارسنجی/ذخیره به لاتین تبدیل کنید؛ در نمایش فارسی کنید.
- انتقال وضعیت سفارش تنها بر اساس `ORDER_STATUS_FLOW` در `@yuma/types`.
- تعطیلات رسمی از پیکربندی خوانده می‌شوند، نه hardcode.

## کد فارسی: جزئیات نگارشی

- نیم‌فاصله (`\u200C`) در واژه‌هایی مثل «شست‌وشو»، «می‌شود»، «خشکشویی‌ها» استفاده شود.
- «ی» و «ک» فارسی (`U+06CC`, `U+06A9`) به‌کار رود، نه عربی (`U+064A`, `U+0643`).
- گیومه فارسی «…» برای نقل‌قول، نه `"…"`.
- اعداد داخل متن با ارقام فارسی نوشته شوند.

## API

- پیشوند همه مسیرها `api`؛ نسخه‌بندی در فاز بعد (`/api/v1`) در نظر گرفته شود.
- پاسخ موفق: `{ ok: true, data }` — پاسخ خطا: `{ ok: false, message, errors?, path, timestamp }`.
- کدهای وضعیت به‌درستی استفاده شوند: ۲۰۰/۲۰۱، ۴۰۰ اعتبارسنجی، ۴۰۱ احراز هویت، ۴۰۳ دسترسی، ۴۰۴ یافت نشد، ۴۲۹ محدودیت نرخ.
- مستندسازی Swagger برای هر endpoint الزامی است (`@ApiTags`, `@ApiOperation`).
- شکست یکپارچه‌سازی بیرونی (پیامک، ایمیل، نقشه) نباید جریان کاربر را متوقف کند؛ لاگ بگیرید و با آرامش Degrade کنید.

## HTTP بیرونی و پروکسی

- از کلاینت HTTP داخلی NestJS (`HttpService` روی Axios) استفاده کنید، نه `fetch` پراکنده.
- پروکسی از محیط خوانده می‌شود:

  ```env
  HTTP_PROXY=http://proxy.corp:8080
  HTTPS_PROXY=http://proxy.corp:8080
  NO_PROXY=localhost,127.0.0.1,.local
  ```

- `NO_PROXY` را برای میزبان‌های محلی/داخلی همیشه تنظیم کنید.
- اعتبارسنجی گواهی فعال بماند؛ خاموش‌کردن آن فقط با دلیل مستند در محیط تست/پروکسی مورد اعتماد.

## تست

- هر تابع بومی‌سازی در `packages/persian` تست واحد دارد.
- هر اسکیما در `packages/validators` تست دارد (ورودی معتبر، نامعتبر، نرمال‌سازی).
- تست هر پکیج کنار کد است: `tests/` برای پکیج‌ها، `*.spec.ts` برای NestJS.
- نام تست فارسی یا توصیفی-روشن باشد تا گزارش تست قابل فهم بماند.
- پیش از commit: `pnpm lint && pnpm test`.

## Git

- پیام commit یک‌خطی و در وجه «چرا»؛ مثال: «افزودن قالب‌بندی تاریخ جلالی با JDN بدون وابستگی بیرونی».
- شاخه‌ها: `feat/...`، `fix/...`، `chore/...`، `docs/...`.
- کوچک نگه‌داشتن PR و پرهیز از تغییرات پراکنده بی‌ربط.

## دسترس‌پذیری و UI

- کنتراست رنگ مطابق WCAG AA.
- همه دکمه‌های آیکونی باید `aria-label` / `accessibilityLabel` فارسی داشته باشند.
- وضعیت‌ها فقط با رنگ منتقل نشوند؛ متن یا آیکون هم باشد.
- در وب، اندازه فونت پایه حداقل ۱۶px و ارتفاع خط راحت برای فارسی.
