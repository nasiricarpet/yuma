## اصول

1. **تک‌منبع حقیقت برای بومی‌سازی.** هیچ اپی منطق تاریخ/عدد/پول را خودش پیاده نمی‌کند؛ همه از `@yuma/persian` می‌آید.
2. **منطق دامنه در سرور.** اپ‌های موبایل و پنل‌ها فقط نمایش می‌دهند و اقدام را به API می‌سپارند.
3. **مرزهای روشن.** هر اپ فقط از طریق API با بقیه حرف می‌زند؛ اشتراک‌گذاری کد فقط از طریق `packages/*`.
4. **قابل‌تست بودن.** توابع بومی‌سازی خالص (pure) هستند و بدون دیتابیس یا شبکه تست می‌شوند.

## وابستگی‌ها

```
config  ──┐
types   ──┼──► ui ──► اپ‌ها
persian ──┤
validators ──► (persian)
db ──► (config, types)
```

- `persian` هیچ وابستگی بیرونی ندارد؛ همه محاسبات تقویم با حساب JDN پیاده شده‌اند.
- `validators` روی `zod` (v4) و `persian` بنا شده است.
- `ui` روی React (وب) و React Native (بخش `./native`) کار می‌کند.

## اپ API (NestJS)

```
apps/api/src/
├── main.ts                  bootstrap + TZ + Swagger
├── app.module.ts            ماژول ریشه
├── app.controller.ts        ریشه و ping
├── health/                  سلامت + تاریخ شمسی
└── common/
    ├── messages.fa.ts       همه پیام‌های فارسی
    ├── all-exceptions.filter.ts   خروجی خطای یکدست فارسی
    └── persian-validation.ts      ValidationPipe با پیام فارسی
```

نقاط مهم:

- در `main.ts` پیش از هر چیز `process.env.TZ = 'Asia/Tehran'` تنظیم می‌شود.
- پیشوند همه مسیرها `api` است و Swagger روی `/docs`.
- هر پاسخ موفق `{ ok: true, ... }` و هر خطا `{ ok: false, message, errors, path, timestamp }` است.
- محدودسازی نرخ درخواست (Throttler) به‌صورت سراسری فعال است.

ساختار پیشنهادی هر دامنه در فاز ۱:

```
src/orders/
├── orders.module.ts
├── orders.controller.ts     HTTP، DTO، مستندسازی
├── orders.service.ts        منطق دامنه و انتقال‌های وضعیت
├── dto/                     class-validator + پیام فارسی
└── orders.repository.ts     دسترسی داده (Prisma)
```

## دیتابیس (Prisma)

- همه نام‌های جدول و ستون در دیتابیس `snake_case` هستند (`@map` / `@@map`) و در TypeScript `camelCase`.
- مبالغ **همیشه** `Int` به ریال هستند؛ هیچ ستون اعشاری برای پول وجود ندارد.
- زمان‌ها `DateTime` میلادی (UTC) ذخیره می‌شوند؛ تبدیل به شمسی فقط در لایه نمایش انجام می‌شود.
- مدل‌ها: `User`, `RefreshToken`, `Laundry`, `LaundryService`, `Driver`, `DriverLocationLog`, `Order`, `OrderItem`, `OrderStatusHistory`, `Assignment`.

## چرخه وضعیت سفارش

```
pending → confirmed → picked_up → in_progress → ready → out_for_delivery → delivered
                                                ↘ cancelled / failed / returned
```

منبع حقیقت در `@yuma/types`:

- `OrderStatus` — فهرست وضعیت‌ها
- `ORDER_STATUS_FLOW` — انتقال‌های مجاز از هر وضعیت
- `ORDER_STATUS_LABELS` — برچسب فارسی هر وضعیت

## تصمیم‌های ثبت‌شده (ADR خلاصه)

| تصمیم | دلیل |
| --- | --- |
| مبالغ به ریال (عدد صحیح) | جلوگیری از خطای شناور و هم‌راستایی با بانکداری ایران |
| نمایش به تومان | عرف کاربران ایرانی |
| تقویم بدون کتابخانه بیرونی | کاهش سطح حمله و وابستگی؛ محاسبه JDN قابل تست و دقیق |
| Turborepo + pnpm workspace | ساخت یکپارچه و کش‌شده همه اپ‌ها با نسخه‌های سازگار |
| Prisma به‌جای ORM عمومی | مهاجرت‌های شفاف و تایپ‌های تولیدشده |
| خطاهای فارسی در لبه (filter) | جلوگیری از تکرار پیام فارسی در هر سرویس |

## مسیر فازهای بعدی

1. **فاز ۱ — بک‌اند:** احراز هویت با OTP پیامکی، مدیریت سفارش، تخصیص راننده، محاسبه قیمت.
2. **فاز ۲ — پنل‌ها:** CRUD خشکشویی و خدمات، داشبورد مالی، گزارش‌های شمسی.
3. **فاز ۳ — موبایل:** جریان کامل ثبت سفارش، پیگیری زنده، اعلان‌ها.
4. **فاز ۴ — پرداخت:** درگاه ایرانی، تسویه با خشکشویی، فاکتور رسمی.
